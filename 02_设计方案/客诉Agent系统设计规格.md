# 制造业品质客诉 Agent 系统设计规格

> 状态：产品方案已确认，待用户审阅本文档后进入实施计划  
> 设计日期：2026-08-19  
> 主要用户：制造业质量经理  
> 正式体验：CloudBase 在线版  
> 故障备份：可双击打开的离线演示版

---

## 1. 背景与产品判断

本作业要求设计一个“制造业品质处理客诉的 Agent 系统”。产品不定位为只负责问答的智能客服，而是帮助质量经理完成客诉受理、风险判断、人工决策、首次响应、追踪闭环和知识沉淀的岗位级数智员工。

核心立场是：**AI 准备材料并提供建议，质量经理对高风险结论和对外承诺负责。**

### 1.1 产品目标

1. 缩短客诉首次响应时间。
2. 提升受理信息完整率。
3. 通过主动进度同步减少客户追问。
4. 在客户接受处理结果、高风险事项清零后完成关单。
5. 将质量经理的修改和判断沉淀为可审核、可复用的企业知识。

### 1.2 非目标

第一版不实现以下内容：

- 通用低代码 Agent 平台。
- 可任意拖拽节点的 Workflow 编辑器。
- 真实 ERP/MES 生产环境对接。
- 无人审批的全自动客诉处理。
- 凭客诉描述自动宣布根因、责任、赔偿或召回。
- 将 Demo 模拟数据包装成真实企业成果。

## 2. 方法论映射

### 2.1 721 理论

70/10/20 是能力来源的方法论，不是精确的算法权重。

| 能力来源 | 系统中的具体实现 |
|---|---|
| 70% 大模型能力＋公开知识 | 客诉理解、信息抽取、缺失追问、风险建议、首响及 8D 初版生成；公开方法论包括 8D、5Why、5W2H 和质量风险原则 |
| 10% 企业历史数据 | 企业 SOP、历史 8D、产品与批次资料、客户特殊要求、风险与 SLA 规则的上传、检索和引用 |
| 20% 人与 Agent 交互沉淀 | 记录 AI 建议、人工修改、修改原因和最终结果；关单后生成待审核知识卡，审核通过后供后续案件检索 |

### 2.2 知识沉淀四步

```text
隐性知识显性化
质量经理修改 AI 判断并记录原因
        ↓
显性知识标准化
Agent 整理为问题、根因、措施、证据和适用范围
        ↓
标准知识组织化
质量经理审核并添加产品、工序、缺陷和风险标签
        ↓
组织知识智能化
后续客诉检索并引用该已审核知识
```

### 2.3 三层产品架构

| 层级 | 本项目实现 |
|---|---|
| 标准化平台能力 | 文档理解、模型网关、企业资料检索、案件状态机、人工审批和操作记录 |
| 场景模板 | 固定的“品质客诉 8D 处理模板” |
| 少量定制 | 各阶段 SLA、风险升级条件、默认责任角色、人工闸口、客户同步频率和关单条件 |

ERP/MES 在第一版仅作为接口扩展点和模拟数据源，不声称已完成真实对接。

## 3. 核心体验与任务流

面试官以“制造业质量经理”身份完成一次真实判断，而不是观看一段预设动画。

### 3.1 主任务

1. 使用用户名 `linghe` 和已配置密码登录在线系统。
2. 选择“开始示例体验”或“新建真实客诉”。
3. 输入客诉文本，可附加图片或 PDF/TXT/Markdown 资料。
4. Agent 抽取事实、发现缺失信息、评估风险、检索企业历史知识并给出建议。
5. 质量经理修改或确认事实、风险、责任部门、SLA 和是否启动 8D。
6. 系统生成客户首次响应、内部工单、D1–D3 初版和 24h/14d/30d 交付时间表。
7. 质量经理审批对外内容并启动处理。
8. 沿固定 Workflow 推进调查、对策、客户确认和关单。
9. 关单后审核 Agent 生成的知识卡。
10. 创建相似案件，验证刚审核的知识能被检索和引用。

### 3.2 固定 Workflow

```text
受理 → 信息确认 → 风险判断 → 人工审批
→ 首次响应 → 临时遏制 → 根因调查
→ 对策验证 → 客户确认 → 关单 → 知识沉淀
```

不提供任意节点拖拽。管理者仅可配置阶段 SLA、高风险条件、默认责任角色、必须人工确认的节点、客户同步频率和关单必备条件。

## 4. AI 与人工的责任边界

### 4.1 AI 自动完成

- 客诉文本与支持的附件理解。
- 产品、批次、缺陷、数量、影响和客户诉求抽取。
- 缺失信息发现和追问生成。
- 风险、责任部门、SLA 和是否启动 8D 的建议。
- 企业资料检索、相似案例展示和“疑似反复”提示。
- 客户首响、内部工单、8D 初版和进度同步草稿。
- 关单后的待审核知识卡生成。

### 4.2 质量经理必须确认

- 最终严重度和安全、召回、合规风险。
- 是否启动 8D。
- 对外回复和时间承诺。
- 责任归属和“首次/反复”最终判定。
- 根因、永久对策和验证结果。
- 客户是否接受处理结果。
- 是否关单。
- 知识卡是否审核通过。

### 4.3 AI 禁止自动完成

- 仅凭客诉描述确定根因。
- 自动承诺赔偿、召回或责任归属。
- 将建议措施标记为已执行。
- 在高风险事项未清零时关单。
- 将未审核的模型输出写入正式知识库。

## 5. 页面与信息架构

### 5.1 一级导航

1. **工作台**：案件列表、待判断、SLA 风险和关单状态。
2. **知识库**：企业资料、历史案例、已审核知识卡和待审核卡。
3. **流程模板**：查看固定客诉 Workflow 并配置少量规则。
4. **方案说明**：展示 721、三层架构、能力边界和演示指引。

“方案说明”与真实业务页分开，不作为案件 Workflow 节点。

### 5.2 工作台

首页优先显示“开始示例体验”和“新建真实客诉”，其次显示待人工判断、即将超时、处理中、待客户确认和已关单案件。

指标仅展示可从实际案件计算的数据：案件数、平均首响时间、平均信息完整率、按时响应率和关单数。“客户追问减少”只作为长期目标，不在单次 Demo 中伪装成已验证成果。

### 5.3 新建客诉与 Agent 分析

页面按“投诉原文与附件 → Agent 分析 → 质量经理判断”组织。

Agent 输出：

- 抽取的客户、产品、批次、缺陷、数量、影响和诉求。
- 缺失字段和建议追问。
- 信息完整率。
- 风险等级、命中依据、责任部门和 SLA。
- 是否建议启动 8D。
- 相似历史案例及引用片段。
- “首次发生/疑似反复”建议。
- 整体置信度和每项判断依据。

信息不足时允许保存为“待补充”，但不允许批准正式对外内容。

### 5.4 案件处理台

案件详情包含四个业务视图：

- **处理进度**：展示 Workflow、责任人、待办、证据、SLA 和操作记录。
- **8D 初版**：展示 D1–D3 已确认内容与 D4–D8 后续计划。
- **客户视图**：仅展示已审批的对外进度、承诺、措施和报告。
- **人机协作记录**：对比 AI 原建议、质量经理修改、修改原因和最终结果。

### 5.5 知识库

第一版支持 PDF、TXT 和 Markdown，同时提供文本粘贴入库。上传后可查看文档解析状态、分段结果、标签和检索引用。

知识使用两组元数据，避免将“内部文档”与 SOP、FAQ 等重叠概念放在同一级：

- **来源属性**：企业正式资料、公开方法论、历史案件、人机交互沉淀。
- **知识类型**：制度规则、SOP、FAQ、流程说明、系统操作路径、客户话术、产品/工艺规范、历史 8D 案例、升级与责任关系。

知识库不将所有文档强制转换为普通 QA。系统保留原始分段和引用，并根据类型生成待审核的问答卡、步骤卡、规则卡、操作导航卡、话术模板或案例卡。模型生成的条目只有审核通过后才能参与正式检索和回答。

关单案例卡包含：问题现象、产品与工序、已验证根因、临时措施、永久对策、验证结果、适用范围、来源案件、审核人和版本。

## 6. 信息可信度与引用规则

每项结论必须同时使用文字标签和视觉区分，不仅依赖颜色。

| 标签 | 含义 | 是否可直接对外 |
|---|---|---|
| 已确认事实 | 来自投诉原文、企业系统或人工确认 | 经审批后可以 |
| 企业知识 | 来自已审核企业资料，附文档和片段引用 | 作为依据，不等于本案事实 |
| AI 抽取 | 模型从原文中抽取，可回溯和编辑 | 须人工确认 |
| AI 建议 | 风险、分派、归因或措施建议 | 不可直接对外 |
| 待验证 | 根因假设、影响范围和对策效果 | 不可作为最终结论 |
| Demo 模拟 | 为演示时间推进而载入的后续调查材料 | 仅用于演示 |

系统不允许模型将“AI 建议”直接升级为“已确认事实”。

## 7. 8D 初版规格

客户要求当天获得的是 **8D 初版（D1–D3＋后续计划）**，而不是伪造已经完成调查和验证的 D4–D8 终版。

### D1 团队

- Agent 根据客诉类型建议质量、生产、工程、供应链和销售角色。
- 质量经理确认团队、负责人和职责。

### D2 问题描述

- 使用 5W2H 整理已确认事实。
- 明确列出缺失信息和待确认事项。
- 不把初步假设写成根因结论。

### D3 临时遏制

- 措施字段包含建议动作、负责人、截止时间、执行状态和证据。
- “建议冻结库存”和“已冻结库存”必须是两个不同状态。

### 后续交付计划

| 时间点 | 对客户的交付 |
|---|---|
| 24h | 完成首次响应、风险升级、临时遏制并更新 D1–D3 |
| 14d | 完成根因调查、永久对策和初步验证，交付 D4–D6 更新 |
| 30d | 完成效果验证、横向展开、客户确认和 D7–D8 闭环；如未达成，则更新原因与新计划 |

30 天是目标交付点，不代表系统到时自动关单。

## 8. 企业知识检索与沉淀

### 8.1 文档到受控知识条目

```text
原始文档
→ 解析与分段
→ 标记来源属性、知识类型和适用范围
→ 生成待审核知识条目
   ├─ FAQ → 问答卡
   ├─ SOP/流程 → 步骤卡
   ├─ 制度规则 → 条件/结论规则卡
   ├─ 系统路径 → 操作导航卡
   ├─ 客户话术 → 场景话术模板
   └─ 历史 8D → 案例卡
→ 知识负责人审核
→ 发布参与检索
```

每条发布知识必须包含来源文档、引用片段、负责人、版本、生效时间、失效时间、适用的工厂/客户/产品/工序、权限等级和审核状态。

### 8.2 轻量 RAG

第一版采用可验证的轻量检索增强：

```text
上传或粘贴资料
→ 提取文本
→ 分段
→ 建立关键词/BM25 索引
→ 检索最相关片段
→ 将 Top 3 片段和引用信息送入模型
```

这是真实的检索增强，但不依赖向量数据库。当个人套餐的 CloudBase 知识库高级能力可用且符合配额时，检索服务可替换为 CloudBase 知识库，但前端、引用规则和业务流程不变。

只有已审核、在有效期内、当前用户有权查看且适用范围与当前案件一致的知识可参与检索。多个有效来源互相冲突时，系统不自行选择，转知识负责人或质量经理确认。

检索无结果、结果低于经测试集校准的阈值或证据不足时，必须显示“未检索到足够的企业历史依据”并转人工。通用方法论只能作为“AI 建议”，不能伪装成企业规定。

### 8.3 受控问答规则

系统区分两种输出模式：

- **知识问答模式**：答案只能使用已命中的已审核知识，每个关键事实必须有引用。信息缺失时不允许自行补全。
- **案件辅助模式**：可以给出风险、追问和处理建议，但必须标记为“AI 建议/待验证”，不得表述为企业已知事实。

知识问答只有在以下条件同时满足时才返回实质答案：

1. 至少命中一条已审核且在有效期内的企业知识。
2. 产品、工厂、客户或流程的适用范围与当前问题一致。
3. 当前信息足以判断知识条目的适用条件。
4. 来源之间不存在无法解决的冲突。
5. 当前用户有权查看该知识。

问答系统禁止自行生成未在已审核知识中出现的电话、邮箱、联系人、系统账号、操作路径、赔偿标准、责任归属、召回结论或企业策略。

### 8.4 人机交互沉淀

每项 AI 建议支持“接受、修改、驳回”。修改和驳回时记录原因。

关单后，Agent 将案件事实、已验证根因、对策、证据、适用范围和人工修改整理为待审核知识卡。只有审核通过的卡片可被后续案件检索。

### 8.5 三层路由与人工接管

每次客诉或知识问答先经过三层判断：

```text
第一层：是否属于制造业品质客诉范围
        ↓
第二层：是否属于安全、召回、合规、重大停线等高风险客诉
        ↓
第三层：现有信息和已审核知识是否足以处理
```

| 判断结果 | 系统动作 |
|---|---|
| 不属于品质客诉 | 说明当前 Agent 的能力边界，推荐对应团队并生成转交摘要 |
| 属于普通品质客诉且证据充分 | 返回受控答案或进入正常案件流程 |
| 信息不足 | 先提出有限追问；仍不足时转人工 |
| 需要 ERP/MES 等系统查询 | 不猜测系统数据，生成查询待办或转人工 |
| 高风险或紧急个案 | 完成受理和风险提示后立即升级，禁止自动实质承诺 |
| 知识未覆盖、命中不足、过期或冲突 | 明确说明证据不足并转人工 |
| 用户明确要求人工 | 立即转人工，不继续阻拦 |

转人工不得只显示一个按钮。系统生成可追溯的“人工接管包”，包含客诉原文和附件、已确认事实、缺失信息、风险信号、已检索知识和未命中原因、AI 已完成的判断、建议接管团队、SLA 以及可向客户发送的过渡回复。

除上述情况外，以下条件也触发人工接管：涉及赔偿、责任认定、召回或正式对外承诺；模型结构错误或置信度过低；客户连续否定答案；文档解析失败；当前用户无权查看命中知识；相似案例在产品、工序或根因上不具备可比性。

### 8.6 知识治理与安全

- 新旧版本冲突时，仅使用当前有效且已审核版本；无法确定时转人工。
- 文档删除、替换或失效时，系统标记受影响的知识条目并停止其参与检索。
- 按工厂、客户、产品和角色控制文档与知识的查看权限。
- 联系方式、客户数据和个人信息按最小必要原则展示并支持脱敏。
- 上传文档的内容始终被视为业务资料，不得把文档中“忽略系统规则”“执行操作”等文字当成 Agent 指令。
- 知识库运营页展示未覆盖问题、低命中问题、常见转人工原因、待审核知识和受影响版本，形成持续补库入口。

## 9. CloudBase 在线架构

```text
CloudBase 静态网站托管
└─ 前端单页应用
   ├─ CloudBase 用户名认证
   └─ 调用 CloudBase 云函数
      ├─ 大模型 API
      ├─ CloudBase 云数据库
      └─ CloudBase 云存储
```

### 9.1 认证

在线版使用 CloudBase 用户名认证创建 `linghe` 账号。密码由 CloudBase 认证服务管理，不在前端或 GitHub 中明文存储。

离线备用版的登录只是 Demo 入口，不声称具有真实认证安全性。

### 9.2 云函数

| 云函数 | 责任 |
|---|---|
| `analyzeComplaint` | 依次执行品质客诉范围、高风险和可回答性判断；检索企业知识、调用模型、校验结构并写入分析记录 |
| `generateInitialPack` | 在人工确认后生成首响、工单、D1–D3 和后续计划 |
| `ingestKnowledge` | 提取上传文档文本、分段、标记来源与知识类型、生成待审核条目并建立检索信息 |
| `searchKnowledge` | 按权限、有效期、适用范围和审核状态过滤，返回带文档名、片段位置和相关度的 Top 3 企业知识 |
| `createHandoff` | 将案件事实、缺失信息、风险、检索过程、转交原因、建议团队、SLA 和过渡回复写入人工接管包 |
| `advanceCase` | 校验当前 Workflow 状态、必填信息和人工闸口后推进案件 |
| `closeCase` | 校验根因、措施、验证、客户确认和高风险状态后关单 |
| `draftKnowledgeCard` | 根据关单案件和人机修改记录生成待审核知识卡 |

### 9.3 数据集合

| 数据集合 | 核心数据 |
|---|---|
| `cases` | 投诉原文、事实、完整率、风险、责任人、SLA、8D 决策、当前状态、客户视图和关单结果 |
| `case_events` | 操作人、时间、AI 建议、人工修改、修改原因、状态变更和证据引用 |
| `documents` | 文档名、类型、存储地址、解析状态、标签、版本和审核状态 |
| `knowledge_chunks` | 文档 ID、文本片段、顺序、关键词、检索分值和引用位置 |
| `knowledge_items` | 条目类型、问题/适用条件、答案/步骤/规则/话术/案例内容、来源引用、适用范围、权限、负责人、审核人、版本、生效/失效时间和状态 |
| `workflow_config` | SLA、风险升级条件、默认责任角色、人工闸口、同步频率和关单条件 |
| `model_usage` | 案件 ID、调用类型、模型、延迟、Token 数、结果状态和错误类型 |

### 9.4 云存储

客诉图片和企业原始文档保存在云存储。数据库只保存存储地址、文档元数据、已提取文本和引用关系。

## 10. 模型调用设计

第一版通过服务端适配层连接兼容结构化 JSON 输出的模型 API。实际地址、模型名和密钥作为 CloudBase 云函数部署环境变量配置，不写入 GitHub、前端构建产物、数据库或业务日志。

一次完整案件最多包含三次主要模型调用：

1. 客诉分析。
2. 生成首次处理包和 8D 初版。
3. 关单后生成待审核知识卡。

文档分段、BM25 检索、Workflow 流转、登录、案件保存和引用展示不调用模型。

模型输出必须经过结构校验。当输出缺字段或格式错误时，允许一次受控修复；修复失败后进入人工填写，不将无效输出写入正式结论。

如上传客诉图片，仅在部署的模型明确支持视觉输入时进行图片理解；否则只存储图片并要求质量经理手工确认，不伪装图像识别能力。

## 11. 异常处理和风险控制

| 情况 | 系统行为 |
|---|---|
| 不属于品质客诉范围 | 不生成业务答案，说明能力边界并创建对应团队的人工接管包 |
| 关键信息缺失 | 显示待确认字段并生成追问；可保存，不可批准正式对外内容 |
| 低置信度 | 展示候选结果和依据；不自动分派、归因或发送 |
| 安全、召回、合规或人员伤害 | 触发红色硬闸口，禁止普通关单和自动对外承诺，强制指定升级负责人 |
| 无企业知识命中或命中不足 | 明确显示企业历史依据不足，只能将通用方法论标记为 AI 建议，并转人工 |
| 知识过期、权限不足或来源冲突 | 不返回实质答案，记录原因并转知识负责人或质量经理 |
| 需要外部系统查询 | 不猜测 ERP/MES 等系统中的数据，生成查询待办或人工接管包 |
| 相似案例匹配 | 只标记“疑似反复”；须人工对比产品、工序、缺陷和根因 |
| 模型超时或失败 | 记录错误并允许一次人工重试；仍失败则进入手工处理或离线预设案例 |
| 模型输出结构错误 | 执行一次受控修复；仍失败则不写入正式结论 |
| 文档解析失败 | 保留原文件，标记解析失败，允许重试或粘贴纯文本；失败文档不参与检索 |
| 网络中断 | 已保存案件从数据库恢复；演示时可切换离线备用版 |

## 12. 关单规则

关单必须同时满足：

1. 必填事实完整。
2. 根因已经人工确认。
3. 临时措施有执行记录和证据。
4. 永久对策有验证结果。
5. 客户接受结果已记录；如客户未接受，不允许正常关单。
6. 未完成的高风险事项为零。
7. 8D 状态与当前阶段一致。

关单后才允许生成待审核知识卡。

## 13. 安全、成本与运行边界

### 13.1 密钥与权限

- 模型 API 密钥和云资源凭据不进入前端、GitHub、数据库或日志。
- 部署时通过 CloudBase 云函数环境变量或密钥管理能力配置。
- 使用最小权限执行身份，不在应用中使用主账号云 API 密钥。
- 关键数据写入、Workflow 推进、关单和知识审核经过云函数，不允许前端绕过业务校验直接写入。

### 13.2 调用成本

- 默认案例结果可缓存。
- 每次分析最多向模型发送 Top 3 企业知识片段。
- 限制单案输入长度、输出长度、每日案件数和模型调用次数。
- 不提供无限开放式聊天。
- 模型失败不进行无限自动重试。
- 图片理解只在上传图片且模型支持时调用。

CloudBase 个人版的具体容量、调用、出网和 AI 能力配额在部署前以账号控制台的当前套餐为准，本文档不根据套餐价格推断配额。

---

## 14. 离线故障备用版

离线版与在线版使用同一套主界面，可双击本地文件打开，不依赖网络、CloudBase 或模型 API。

离线版完整支持两个内置案例：

1. 支架尺寸超差主案例。
2. 信息不足且疑似安全风险的边界案例。

离线版能完成人工判断、首次处理包、Workflow 推进、模拟后续证据载入、关单和知识卡审核，但必须标记“本地备用结果”和“Demo 模拟”。

离线版不承诺理解任意自由输入，不将预设结果伪装成真实大模型调用。

## 15. 验收标准

### 15.1 业务验收

1. 普通尺寸超差案件可完整走通分析、人工判断、首响、8D 初版、后续证据、客户确认、关单和知识沉淀。
2. 信息缺失时不允许直接批准正式对外内容。
3. 安全、召回或合规风险触发强制升级。
4. 无企业资料命中时不伪造 RAG 引用。
5. 人工修改可追溯，关单后可生成待审核知识卡。
6. 新案件可检索和引用刚审核的知识卡。
7. 不满足关单条件时不允许关单。
8. 非品质客诉可被范围路由拦截并生成对应团队的转交摘要。
9. 高风险客诉在受理后强制进入人工升级，不等同于普通拒答。
10. 电话、联系人、系统路径和企业策略不在已审核知识中时，系统拒绝自行补全。

### 15.2 系统验收

1. 在线版使用 CloudBase 用户名认证，未登录用户不能进入案件页。
2. 在线案件刷新页面后仍可从云数据库恢复。
3. 上传的知识文档有可见的解析、分段和检索状态。
4. 模型超时、失败或格式错误有明确降级，不显示伪成功。
5. 前端构建产物、Git 历史和业务数据中不存在模型密钥或云资源凭据。
6. 每次模型调用均记录类型、延迟、Token 数、结果状态和错误类型，不记录密钥。
7. 离线备用版在无网络和无 API Key 时可走完两个预设案例。
8. 上传文档生成的知识条目在审核前不参与正式回答。
9. 文档失效或替换后，受影响的知识条目停止参与检索。
10. 文档中的指令性文字不能更改系统规则、权限或工作流。

### 15.3 知识库评估

实施时建立包含“应正确回答、应追问、应拒答/转人工”的标准问题集，用于校准检索阈值并验证：

- 正确知识命中率。
- 引用与答案的一致性。
- 知识未覆盖时的拒答准确性。
- 安全、召回、合规和紧急个案的人工升级召回率。
- 过期、冲突、越权知识被排除的准确性。
- 需要外部系统查询时不虚构结果的准确性。

### 15.4 演示成功标准

- 面试官能在一次体验中真正修改一项 AI 判断并影响后续输出。
- 面试官能看到 Agent 引用的企业历史资料。
- 面试官能识别已确认事实、AI 建议、企业知识和待验证项。
- 面试官能在关单后将一条人机交互经验审核入库，并在新案件中看到它被复用。
- 系统不把 Demo 模拟、AI 建议或相似案例包装成真实调查结论。

## 16. 部署配置边界

实施使用以下部署时配置，但这些值不进入代码仓库：

- CloudBase 环境 ID。
- 模型 API 基础地址、模型名、API Key 和是否支持视觉输入。
- 单案输入/输出长度上限、日调用上限和超时时间。
- CloudBase 个人版当前可用的函数、数据库、存储、静态托管和 AI 配额。

密钥由用户在 CloudBase 控制台或受信任的本地部署环境中配置，不通过聊天消息、截图或仓库文件传递。
